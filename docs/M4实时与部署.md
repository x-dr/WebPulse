# M4 实时与部署

日期：2026-11-06。范围：实时页/SSE、生产镜像、数据库分权、TLS/可信代理、独立删除清单、加密备份和隔离恢复。原 `design/reference/` 与 001–003 迁移保留不变，部署维护源现在是根目录 Compose、`docker/` 和 `ops/`。

## 实时行为

`GET /api/v1/realtime?site_id=…` 使用管理 cookie，拒绝额外日期参数。初次连接返回完整 `snapshot`；携带任意 `Last-Event-ID` 的重连返回完整 `reset`，客户端整体替换。事件 ID 是启动 UUID 加进程内序号，不用于统计结算。

- 每个有订阅的站点共享一个 5 秒快照任务，15 秒注释心跳；没有订阅即释放任务。查询通过短事务复用连接池，SSE 不独占连接。
- 全实例最多 20 条，每管理员最多 3 条。每条写缓冲上限 64 KiB；出现背压后停止排队，5 秒内未 drain 即清理连接。
- 每 60 秒复查会话有效期和撤销；每轮快照检查站点及恢复状态。退出立即关闭已知连接；配置变更/暂停/删除使旧连接失效，需重新连接。
- 页面隐藏暂停、显示后重新取快照，切站点/卸载/退出均释放连接。同源标签通过 Web Locks 与 BroadcastChannel 共用一个流；浏览器不支持时回退到独立流，仍受服务端限额约束。
- 展示滚动 15 分钟活跃、最近 60 秒 PV、15 个自然分钟桶、活跃页面 Top 10 和最近 20 条脱敏页面。2026-11-06 增补的真实 IP 记录包含在最近页面 `client_ip` 中，旧事件为 null。访客当前页面使用既有服务器活动顺序；不返回访客键、IP 键或会话 ID。延迟/维护/等待不显示为零。

## 生产拓扑与权限

推荐主机至少 2 GiB；主机运行预先构建的镜像。`db`、`api`、`worker`、`web` 的硬上限分别为 384/256/192/48 MiB；这些是上限配置，不是已测吞吐承诺。API 池最大 7，维护进程最大 1；迁移/运维使用独立短时进程，升级时先停 API/worker/web，给运维留内存和连接。1 GiB、完整保留窗口和 24 小时混合负载归 M5。

| 进程/凭据                  | 权限与材料                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------ |
| `webpulse_owner` / ops     | 显式迁移、角色准备、管理员创建、备份/恢复；不用于 HTTP                               |
| `webpulse_app` / API       | 读取报表、必要采集/配置写入；不具备 DDL、管理员创建或事实/站点删除权限；只有删除公钥 |
| `webpulse_worker` / worker | 维护与删除的业务 DML，无 DDL；持删除私钥和独立清单访问 token，无 HMAC 身份密钥挂载   |
| journal 服务               | 独立 TLS、签名密钥和访问 token；没有数据库凭据和删除私钥                             |

`database:prepare` 显式执行迁移及授权，重复执行安全；遇到已有高权、继承或拥有对象的运行角色会拒绝。密码以 SCRAM verifier 进入 SQL。运行角色不能修改迁移历史；API 不会自动迁移。`004_deployment.sql` 新增备份台账、持久化恢复闸门/重放记录和删除完成清单确认字段。

API/Web 均为非 root、只读根文件系统、无额外 capabilities。API/数据库不映射公网端口。Nginx 终止 TLS 1.2/1.3 和 HTTP/2，覆盖 forwarded 头；Fastify 只信任配置中的固定 Nginx 地址。默认关闭代理信任，拒绝 `true` 和 `/0`。CDN/其他代理须另行明确地址及原始 IP 验证。

Nginx 仅记录时间、请求 ID、方法、状态和耗时，隐藏公网健康接口；SSE 单独关闭缓冲/压缩/缓存，读超时 75 秒。静态后台支持路由回退，SDK 单独缓存。Web 内部健康探针只检验本容器 TLS 服务可响应；外部证书信任仍应由部署后的客户端检查。

## 首次部署

下面命令从仓库根运行。用于自己的生产主机前，准备 DNS、受信任证书和独立清单服务；这里不签发公网证书，也不发布镜像。

构建机执行：

```bash
docker build -f docker/Dockerfile --target api -t webpulse-api:0.1.0-m4 .
docker build -f docker/Dockerfile --target web -t webpulse-web:0.1.0-m4 .
# 将镜像保存或发布到自己的仓库；目标主机使用相同已核对的镜像。
docker image inspect webpulse-api:0.1.0-m4 webpulse-web:0.1.0-m4
```

当前 Dockerfile 固定 Node 24.22.2（构建为 Bookworm、运行时为移除 npm/yarn 的 Alpine）和 Nginx 1.30.6 的 digest，Compose 固定 PostgreSQL 17 Bookworm digest；镜像内冻结安装锁文件，只部署后端生产依赖。M4 当时使用 Node 24.18.0；M5 更新和安全放行限制见 [M5 验收](M5加固与验收.md)。当前实际运行验收为 Linux/amd64，其他平台须重新构建验证。

目标主机：

```bash
test -f .env.production || cp .env.production.example .env.production
sudo node ops/initialize.mjs secrets
```

编辑 `.env.production`：设置实际域名、HTTPS `ADMIN_ORIGIN`、证书目录、独立 journal HTTPS URL 和可信 CA 文件。保留已生成的密钥；初始化脚本只创建不存在的文件。默认容器 UID/GID 为 1000；脚本以 root 运行时把新密钥设为 1000:1000、0400。证书私钥也须对该 UID 可读，证书父目录可遍历。更改私网段时同步修改三个固定地址，不能与宿主现有网络重叠。

`tls/fullchain.pem`、`tls/privkey.pem` 使用实际证书，`JOURNAL_CA_FILE` 使用信任 journal 的 CA PEM。TLS 文件和真实 `.env.production` 均不入 Git。然后执行：

```bash
docker compose --env-file .env.production -f compose.yml up -d --wait db
docker compose --env-file .env.production -f compose.yml run --rm -T ops node dist/cli.js database:prepare
read -r -s -p '管理员密码（至少 12 字符）: ' WEBPULSE_NEW_ADMIN_PASSWORD
printf '\n'
printf '%s' "$WEBPULSE_NEW_ADMIN_PASSWORD" |
  docker compose --env-file .env.production -f compose.yml run --rm -T ops node dist/cli.js admin:create admin
unset WEBPULSE_NEW_ADMIN_PASSWORD
docker compose --env-file .env.production -f compose.yml up -d --wait api worker web
docker compose --env-file .env.production -f compose.yml ps
```

不启动 profile 中的 ops/journal 是默认行为。先建管理员再开放 Web；没有默认账号。迁移不匹配或恢复未验证时 readiness 失败，普通 API 保持 503。证书续期后执行 `docker compose --env-file .env.production -f compose.yml exec web nginx -c /tmp/nginx.conf -s reload`，再检查公网证书有效期与登录。

## GitHub Actions 构建与拉取

[镜像工作流](../.github/workflows/docker.yml) 只接受 `workflow_dispatch` 手动运行；先把文件纳入默认分支，再在 Actions 的 **Build Docker images → Run workflow** 中选择源码分支，填写版本。版本格式为 `0.1.0` 或 `0.1.0-rc.1`，可带 `v` 前缀，发布时去掉该前缀；不接受 `+` 构建元信息。`latest` 默认为关闭，预发布版本禁止更新它。重复使用版本会覆盖对应标签；生产应固定任务摘要中的 digest。

工作流复用 `docker/Dockerfile` 的 `api`、`web` 目标，使用 QEMU/Buildx 构建 `linux/amd64`、`linux/arm64`，按目标缓存构建层；使用 `GITHUB_TOKEN` 的 `packages: write` 发布，不需要额外 PAT 或 Docker Hub Secret。API 镜像同时供 api、worker、ops 和 journal 使用，Web 镜像提供静态后台与 Nginx。配置方式依据 [Docker 多架构构建](https://docs.docker.com/build/ci/github-actions/multi-platform/) 和 [GitHub 发布容器镜像](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images)。

例如仓库为 `Owner/WebPulse`、版本为 `0.1.0` 时，在 `.env.production` 设置：

```dotenv
WEBPULSE_API_IMAGE=ghcr.io/owner/webpulse-api:0.1.0
WEBPULSE_WEB_IMAGE=ghcr.io/owner/webpulse-web:0.1.0
```

将示例路径替换为自己的仓库小写路径；生产可分别改成任务摘要中的 `ghcr.io/owner/webpulse-api@sha256:…` 与 `ghcr.io/owner/webpulse-web@sha256:…`。两个任务的摘要均包含本次版本和 digest，另有 `sha-<完整提交 SHA>` 标签用于追溯源码。

首次发布后分别检查两个 GHCR Package 的可见性。Public 镜像可匿名拉取；Private 镜像须在目标主机先登录，使用有 `read:packages` 权限的访问令牌，通过 `docker login ghcr.io --username YOUR_GITHUB_USER --password-stdin` 从标准输入提供。发布失败时检查组织策略及 Package 的仓库 Actions 访问权限。

完成上文首次部署所需的密钥、TLS、独立清单和环境配置后，目标主机执行：

```bash
docker compose --env-file .env.production -f compose.yml pull api web
docker compose --env-file .env.production -f compose.yml up -d --no-build --pull never --wait db
docker compose --env-file .env.production -f compose.yml run --rm -T --no-build --pull never ops node dist/cli.js database:prepare
# 按上文首次部署步骤创建管理员，再开放服务。
docker compose --env-file .env.production -f compose.yml up -d --no-build --pull never --wait api worker web
```

`--no-build` 防止含 `build:` 的服务意外在目标主机重建；worker/ops/journal 复用已拉取的 API 镜像。已有实例升级前按既有备份与迁移流程停写、备份并验证，不能把上述首次部署命令当作完整升级流程。独立 journal 主机也须使用相同版本 API 镜像。

M5 已加入常规回归和镜像扫描前置闸门；数据库镜像的扫描阻断项未清除时不会发布。实际 GHCR 发布结果、多架构清单与 ARM64 运行行为须在执行 Actions 后单独核验；本地检查不代表在线发布成功。

## 独立删除清单

HTTP 服务用 RSA 3072 公钥封装一次性 AES-256-GCM 密钥，维护进程才持有解密私钥。本地旧的对称密钥入口保留用于开发；生产 HTTP 拒绝私钥/对称删除密钥。私钥及匹配 key ID 缺失时删除和恢复均失败关闭。

journal 的意图按 task ID 幂等追加，完成结果另行追加；记录使用独立 HMAC 链及连续序号认证。临时文件 fsync → 原子替换 → 目录 fsync 完成后才确认。服务单写者，必须显式 `journal:init`；已有清单不可覆盖，丢失存储不会自动创建空清单。上传后数据库确认前崩溃，重试得到原序号；确认前不执行破坏性批次。达到当前 4 MiB 清单容量上限会停止受理，保留原清单和数据库闸门；不要删除清单腾空间，扩容/分段与规模复测归 M5。

生产优先将 journal 放在另一主机及独立持久存储上。`compose.journal.yml` 可单独运行；仅需同版本 API 镜像、匹配 `journal_token.txt`/`journal_signing_key.txt`、受信任 TLS 证书和 `JOURNAL_DATA_DIR`。目录应归 1000:1000、0700，密钥 0400。只运行一个写者，持久目录不随数据库恢复或七日备份轮转回退。

在独立清单主机配置同名路径变量后，首次执行：

```bash
docker compose --env-file .env.production -f compose.journal.yml run --rm -T journal node dist/cli.js journal:init
docker compose --env-file .env.production -f compose.journal.yml up -d journal
```

已经初始化的存储只执行第二条。主应用 worker 通过 `DELETION_JOURNAL_URL` 和 token 访问它；ops 的恢复校验另外需要匹配签名密钥。独立备份清单及必要密钥，不能仅保留数据库卷。根 Compose 的 `local-journal` profile 供单机隔离验收使用：独立目录但仍是同一宿主故障域，不能作为异机耐久证据。

## 备份与确认销毁

目标策略：每日数据库快照和匹配密钥，加密后异机保留至少 7 日。先在离线管理机生成独立 RSA 3072 备份密钥对，仅把公钥放到备份主机；解密私钥留在离线/恢复环境，和服务器分开保管。

```bash
BACKUP_PUBLIC_KEY_FILE=/secure/backup-public.pem \
BACKUP_SECRET_DIR=/srv/webpulse/secrets \
BACKUP_DIR=/srv/webpulse/backups \
WEBPULSE_ENV_FILE=/srv/webpulse/.env.production \
  node ops/backup.mjs
```

脚本从一致性 `pg_dump -Fc --no-owner --no-acl` 读取，流式 RSA-OAEP-SHA256 + AES-256-GCM 加密；失败不发布成功文件。输出同 UUID 的 `.db.wpbackup`、`.keys.wpbackup` 和 `.json`。密钥包保留数据库密码、三份 HMAC、删除密钥对、journal 材料，以及 secrets 目录中存在的 `visitor_hmac_history.json`。manifest 记录两个密文校验值、快照开始边界、完成时间、数据库身份 epoch、删除 key ID 和 journal head；数据库 `backup_inventory` 记录对应备份。快照开始边界在 pg_dump 前取数据库时间，不能当作精确的导出事务提交时刻。

把三个文件传到异机，独立校验 manifest 中的两个 SHA-256，记录异机位置，再纳入日轮转。脚本不自动上传、删除备份或销毁清单；应把异机校验纳入自己的调度。外部 manifest 也要保留，恢复的旧数据库未必已包含该备份自己的台账行。

只有确认全部相关副本（包括人工和恢复副本）已销毁，才记录相应台账：

```bash
printf '%s' '{"id":"替换为备份UUID","all_copies_destroyed":true}' |
  docker compose --env-file .env.production -f compose.yml run --rm -T ops node dist/cli.js backup:mark-destroyed
```

这个命令只记录操作者的确认，不删除文件，不释放密钥/清单。七日不是清单 TTL；相关备份未全部确认销毁前持续保留删除意图、完成记录、匹配解密材料和最小 tombstone。

## 隔离恢复

先关闭原入口和写入，保留原数据库卷。恢复环境使用匹配版本镜像，不向公网开放；独立 journal 保持最新，不随旧数据库回退。首次恢复到空主机时，先用离线私钥恢复匹配密钥，已存在但不同的文件会拒绝覆盖：

```bash
BACKUP_PRIVATE_KEY_FILE=/offline/backup-private.pem \
  sudo --preserve-env=BACKUP_PRIVATE_KEY_FILE node ops/recover-keys.mjs \
  /restore/备份UUID.keys.wpbackup /srv/webpulse/secrets
```

准备数据库容器、journal CA 和 `.env.production` 后，从仓库根运行：

```bash
RESTORE_DB_NAME=webpulse_restore_drill \
BACKUP_PRIVATE_KEY_FILE=/offline/backup-private.pem \
BACKUP_SECRET_DIR=/srv/webpulse/secrets \
WEBPULSE_ENV_FILE=/srv/webpulse/.env.production \
  node ops/restore.mjs /restore/备份UUID.json
```

脚本只接受新建 `webpulse_restore_*` 数据库，目标存在即失败，不覆盖旧库。先验证密文 checksum/GCM 和匹配密钥，再 pg_restore、迁移/授权、锁定及重放。M4 备份排除 `recovery_state` 数据，恢复后的空闸门会直接阻止入口；早于 M4 的备份在独立目标迁移，不会自动切换现有服务。

若部署命令使用额外 Compose 覆盖文件，备份和恢复均须设置 `WEBPULSE_COMPOSE_OVERRIDE_FILE=/absolute/path/compose.override.yml`，并继续使用相同 `WEBPULSE_ENV_FILE`。两种工具共用参数生成器，避免按不同资源配置重建数据库。

恢复会校验最新完整清单的连续序号和 HMAC、逐条解密，重放**全部意图**，包括快照前已受理但未完成的任务。整站目标不存在也写永久 tombstone；visitor 类型删除精确 key/epoch 对应事实，保守把 cutoff 所在自然日结束前的历史覆盖标为 `privacy_replay_unverifiable`，不提供未证明安全的旧汇总；普通聚合不会清掉这些 gap。重放按 task ID 幂等并持久化进度。缺序、缺私钥/epoch、未入清单的待处理任务、清单变化或删除校验失败，都保持闸门关闭。

全部验证完成才写 `verified` 与 journal head。已有完成记录复用原序号，未完成意图追加恢复完成记录，恢复结果另存 `recovery_replays`；后续维护不重复改写原完成结果。恢复站点仍暂停；先检查残留事实、覆盖提示和业务对账，再显式把隔离 API 指向恢复库验收。切换生产入口及恢复站点采集属于后续部署操作；工具不会自动切换。不可验证历史的 gap 不因重启/恢复采集而清除。

RPO≤24 小时/RTO≤60 分钟仍需结合真实数据量、异机传输和运维流程测量。本次小夹具恢复秒数见机器记录，不能推算生产恢复时间。

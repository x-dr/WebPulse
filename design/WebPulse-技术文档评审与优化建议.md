# WebPulse 技术文档评审与优化建议

评审日期：2026-11-03。评审对象：[项目技术文档 v1.0.0](WebPulse-项目技术文档.md)及 `reference/` 中的 SQL、Compose、Dockerfile、Nginx 和环境模板。

> 2026-11-04 进展：R01–R07 已在主文档 1.1.0 及两份契约修订，R08–R14 已分配实施阶段。见 [M0 设计冻结与验收](../docs/M0设计冻结与验收.md)。以下保留 2026-11-03 的原始评审依据与当时验证边界，不代表修订后的当前状态。

## 评审结论与边界

保留 PostgreSQL，沿用 Fastify、TypeScript、React、Ant Design、ECharts 的架构。多个网站共用数据库、业务表通过 `site_id` 隔离的方向可继续采用。“5 个站点”应定义为初始资源验收规模，不能代替所有站点的合计负载预算。

当前主要工作是补齐统计和数据生命周期的边界，再优化 PostgreSQL 热点写入。建议先解决下列 7 项 P1 问题，再冻结实施基线。P1 表示实现前应明确，否则存在漏计、错计或数据清理与恢复不完整的风险；P2 表示在对应模块实施和上线验收中完善。

本次新增的是评审报告，未修改原技术文档、原 SQL 或部署参考文件。当前目录没有业务应用源码；下列结论是设计评审、SQL 检查和构造反例，不能表述为已经发现线上故障。

## R01：补充独立的到期冻结任务

**依据：**主文档 L1147–1179 只列出会话关闭、脏桶重算等任务；L1187 要求桶结束 12 小时 30 分钟后才能冻结；L1196 要求清理前汇总已完成。

**触发场景：**某日最后一次聚合时桶尚未达到冻结时间，聚合成功后删除了脏标记。此后该站点没有新访问，也没有待结算会话。到达冻结时间时，没有脏桶再次触发聚合，`is_final` 仍为 false。

**影响：**历史查询可能持续回查明细；清理为保护数据而一直等待，最终超出保留预算。

**建议：**增加独立的到期冻结扫描，不以 `dirty_buckets` 是否存在作为唯一调度依据。扫描到期且未冻结的小时/日桶，在一致事务中确认相关会话已结算、汇总版本有效、没有未处理变更，再设置最终状态。没有访问的完整日期也要有可验证的零值覆盖信息。

**验收：**造一个只有一次访问的站点，随后不再写入；时间推进至冻结期限后，应自动冻结，并在保留期到达后正常清理。PGlite 构造已确认“达到期限但没有脏标记的非最终桶”在现有结构中可以存在；尚无真实任务实现可验证其运行行为。

## R02：今日同期比较必须支持部分日期

**依据：**主文档 L356 要求今日只比较昨天相同本地时刻；L750–766 的成员 SQL 只按日期筛选；L1189 又规定范围 UV/IP 始终从日成员去重。

**触发场景：**现在是 10:00。昨天 A 在 09:00 访问、B 在 15:00 访问。昨天的日成员集合有两个人，但昨天截至 10:00 只有一个人。

**已验证：**在原 SQL 建立的 PGlite 数据库中，日成员查询得到 UV=2，按原始 PV 截止时间查询得到 UV=1。

**建议：**区分完整自然日查询与内部同期比较查询。涉及历史日内截止时刻的 UV/IP、新老访客，按实际时间范围从 PV 事实集合精确去重，不能直接读取全天成员或全天汇总。完整日期和部分日期组合时也要对成员集合统一去重，不能相加各段 UV。

跳出率和时长还要明确历史截止时刻：昨天 09:00 开始、11:30 才关闭的会话，不能仅因现在是 closed 就被当作“昨天 10:00 已结束”。建议按 `closed_at <= comparison_as_of` 选择截至当时已经结算的会话，并说明后台结算延迟。若选择其他比较口径，必须在 API 元信息和指标说明中明确。

**验收：**覆盖午后首次访问、跨午夜会话、截止时刻之后关闭的会话、夏令时重复/缺失墙钟时刻，以及无可用明细时的明确不可用结果。

## R03：SPA 导航判重与路径脱敏分离

**依据：**主文档 L408 通过标准化 path 判断路由变化；L426 又将数字 ID、UUID 等替换为 `:id`。

**触发场景：**SPA 从 `/product/123` 导航到 `/product/456`，两次脱敏结果都是 `/product/:id`。若用上报路径判断是否发生新访问，第二次 PV 会丢失。

**建议：**SDK 在内存中以真实导航标识判断是否发生逻辑页面变化；实际发出事件时再按隐私规则清洗路径。原始导航标识不上传、不写日志、不额外持久化。同一 URL 的重复包装调用仍应合并；query/hash 是否构成页面变化继续由明确配置控制。

**验收：**上述两次访问应生成两个 event ID，服务端 PV=2，受访路径 `/product/:id` 的 PV=2。重复 `replaceState` 到同一逻辑地址不重复计数。

## R04：interaction 必须检查会话有效性

**依据：**主文档 L940 规定 interaction 校验页面存在和访客归属；L952 对心跳明确要求拒绝过期/已关闭会话，interaction 没有对应规定。

**触发场景：**页面行仍保留，但会话已经关闭。延迟请求或新的 interaction ID 引用旧页面，若仅验证页面和访客，就可能改变已经结算的互动计数、跳出状态或最近活动时间。

**已验证：**原数据库约束允许为 closed 会话插入 interaction。业务检查应由采集层执行，不能依赖当前外键替代。此项不是实际 API 漏洞结论，因为 API 尚未实现。

**建议：**在与心跳一致的锁顺序下检查 status、30 分钟超时及 12 小时上限。相同已处理事件的重试可按幂等返回成功且不产生副作用；新的过期互动拒绝写入。SDK 不应把旧页面排队的互动直接转移到新会话。

**验收：**关闭会话后发送新互动 ID，统计、活动时间和冻结汇总均不改变；重复已确认事件仍保持幂等。

## R05：重算必须移除消失的排行分组

**依据：**主文档 L1177 要求以完整结果 upsert 汇总与排行；L489 又要求删除单访客后重算受影响日期。

**触发场景：**`/a` 的唯一访问被删除，重算结果只剩 `/b`。单纯 upsert `/b` 不会删除旧的 `/a` 汇总行，来源分组也有同样问题。

**已验证：**对原 `stats_pages_daily` 表执行“事实分组结果 upsert”，删除事实中的一个分组再重算，旧汇总分组仍存在。

**建议：**把“完整替换桶内结果”写成明确事务协议，例如计算结果后，在同一提交中删除该桶消失的键、写入其余结果；或者有界地删除该桶旧结果再插入全量结果。总量为零的桶仍要保留零值、版本和覆盖状态。删除所需事实已过期时，继续遵守原文的不可猜测重建原则。

**验收：**分别测试删除某路径最后一个访客、删除某来源全部会话、清空整日事实和重复执行删除；旧排行必须消失，零值不能被误报为聚合失败。

## R06：持久化删除任务、水位及恢复清单

**依据：**主文档 L890 的 DELETE 返回 `job_id`，端点列表含 `/jobs/:job_id`；SQL 只有按 `name` 记录最近运行信息的 `job_state`。主文档还要求实际保留水位和恢复后重放删除清单，但未明确其字段与状态转换。

**建议：**为下列状态给出可实施契约，可以使用职责清楚的表或严格定义的现有 JSON 结构，但不能仅写“后台处理”。

- 删除任务：任务 ID、站点稳定标识、类型、状态、阶段、批次游标、重试次数、结果、创建/完成时间，以及重启后的恢复规则。
- 覆盖与清理水位：每站点、每数据层的可用边界、聚合/冻结边界和清理进度；只在对应批次提交后推进。空站点不能靠 `min(event_time)` 推导有效保留窗口。
- 恢复删除清单：任务类型、稳定站点标识、精确删除目标和时间语义。现有“任务 ID、站点 ID、日期范围”不足以重放精确单访客删除，除非明确恢复时删除整个范围。

若保留单访客恢复删除能力，使用受限、加密保存的必要访客键及密钥 epoch 信息，避免记录原始 cid；站点删除任务完成后，其结果和必要恢复清单不能随站点外键级联消失。清单应保留至所有可能包含被删数据的备份退出，恢复期间先补做删除再开放报表。

**验收：**删除中途重启后继续完成；清理中途失败不夸大可用窗口；从删除之前的备份恢复后，被删除数据不会重新提供查询。

## R07：明确禁用/删除与采集的并发边界

**依据：**主文档 L140 要求暂停立即停止采集；L278 的站点状态校验位于事务开始之前；后续仅给出概括性的锁顺序。

**触发场景：**请求先检查 enabled=true，随后管理员禁用站点并收到成功，之前的请求又提交统计。只清缓存不能阻止已经通过检查的请求。

**建议：**定义禁用完成的线性化时点，明确管理员操作返回成功后不再出现旧请求的新提交。一种可行实现是采集事务先按统一顺序对站点取共享行锁并复查状态，禁用/删除事务取得冲突写锁，等待之前采集排空后提交。避免为每条采集对站点使用排他行锁，导致全站完全串行。

`FOR KEY SHARE` 不会阻止普通非键字段更新，不能直接假设它足以保护 enabled。具体锁组合应按 [PostgreSQL 行锁规则](https://www.postgresql.org/docs/17/explicit-locking.html)验证；这是建议方案，未做真实多连接验证。

**验收：**在“状态检查后、业务写入前”暂停采集请求，再执行禁用；禁用完成后的所有新请求拒绝，旧请求的提交顺序符合文档约定，删除任务不与新采集反复竞争。

## R08：降低脏桶热点和聚合重试

**依据：**主文档 L1169–1172 每次标脏都会更新同一 `(site_id, grain, bucket_start)` 行；L1177 在 REPEATABLE READ 快照末尾尝试删除它。

同站点的不同访客虽然使用不同访客锁，最终仍会在当前日/小时脏桶更新上竞争。聚合扫描期间该行发生新更新，随后删除时可能遭遇序列化失败，导致整桶重算重试；[PostgreSQL 隔离级别说明](https://www.postgresql.org/docs/17/transaction-iso.html)确认了这种并发更新行为。风险成立，但影响幅度尚未压测。

**建议：**先明确哪些写入真正影响汇总。未关闭会话的心跳只更新活跃信息和待结算时长时，不必反复修改只统计已关闭会话时长的日汇总标记。衡量 PV 热桶的锁等待后，再选择分片脏标记或带版本的持久化变更记录。

聚合可评估“发布某个一致快照的结果，保留更新版本的待处理标记”，避免持续流量下每次都丢弃计算；但必须明确结果版本、快照时间、发布顺序以及冻结条件，不能无条件清脏。也不要为避免重试而在长扫描前锁住热桶、让所有采集等待。

**验收：**持续写入期间测采集 P95/P99、锁等待、聚合重试次数和最老积压；同时确保重跑不重复计数、结果不回退、积压能持续收敛。

## R09：补齐关键外键引用端索引

本次使用 PostgreSQL 系统目录检查了原 SQL。以下外键没有覆盖全部相关行、以前述列顺序开头的有效普通索引，建议优先评估：

```sql
CREATE INDEX events_page_view_idx ON events(site_id, page_view_id);
CREATE INDEX events_visitor_idx ON events(site_id, visitor_key);
CREATE INDEX page_views_session_idx ON page_views(site_id, session_id);
CREATE INDEX sessions_visitor_idx ON sessions(site_id, visitor_key);
```

这些是待验证候选，未加入正式迁移。`sessions_one_open_idx` 只覆盖 open 会话，不能覆盖删除访客时对 closed 会话的完整检查。`admin_sessions(admin_id)` 也没有完整引用端索引，但单管理员和少量登录会话场景优先级较低。

PostgreSQL 不会因声明外键就自动创建引用端索引；缺失时关联删除/检查可能扫描站点内大量无关行，具体计划取决于数据分布和现有索引。[外键与索引说明](https://www.postgresql.org/docs/17/ddl-constraints.html)

**验收：**预置目标保留规模，检查批量页面、会话、访客删除的 `EXPLAIN (ANALYZE, BUFFERS)`、实际耗时和锁等待；同时测新增索引造成的采集写入与磁盘成本。

## R10：多站点公平性与分层超时

当前已有站点/cid 速率限制、全局 64 在途和报表并发限制，应在这些基础上补充每站点的在途占用及任务调度份额，避免高流量站点耗尽全部连接或重算轮次。保留给采集、管理和后台任务的连接总额仍须服从原资源预算，不能每个类别都独立创建一个 max=8 的池。

建议显式区分连接获取期限、锁等待期限、单条 SQL 期限、整笔事务期限和 HTTP 请求总期限。`statement_timeout` 限制单条语句，不等于完整事务；PostgreSQL 17 的 `transaction_timeout` 会终止超时会话，使用它时需配套连接池连接销毁和重建处理。[超时参数说明](https://www.postgresql.org/docs/17/runtime-config-client.html)

SSE、清理、冻结和聚合任务按站点轮转。默认每 cid 12 次/分钟，仅 3 个可见标签页的常规心跳就会占满额度，还没有计算 PV/互动；应写清多标签策略及正常流量不误伤的验收场景。

**验收：**A 站持续突发，B 站维持低负载，B 的采集和管理操作仍可用；断开的报表请求不继续无限占用数据库资源。

## R11：时间顺序和幂等副作用

文档将接收时间作为事件时间，但没有明确它在 HTTP 接入、获取连接还是取得访客锁后取值。多标签并发时，请求到达顺序与取得锁的顺序可能不同；直接覆盖 `last_activity_at` 或 `latest_path` 可能让状态倒退。

建议分别定义接收时间、业务处理顺序及比较规则。最近活动时间必须单调更新；同时间戳页面选择有稳定次序；较早到达但较晚处理的请求如何归入会话、更新首次访问时间和成员快照，应有明确规则。`events.ingest_seq` 只覆盖事件，心跳也参与当前页面选择；不能只凭这个字段就声称所有活动都有持久化顺序。PostgreSQL 的 `now()` 是事务开始时间，也不等于获取锁后的时刻。[时间函数说明](https://www.postgresql.org/docs/17/functions-datetime.html)

重复 PV 的访客 upsert 不应在判重之前更新活动时间或重新开启会话。`payload_fingerprint` 需要列出字段、规范化算法及版本：服务端接收时间、重试时的网络 IP 等可变化信息不应被不加区分地纳入重试一致性判断。

**验收：**较早请求后取得锁、跨日争锁、同毫秒多页面、换网络重试、重复 PV 及规则变更期间重试；所有情况都应满足定义好的幂等和时间归属规则。

## R12：补齐产品契约与保留边界

- 第 3 节要求来源详情，API 只列来源列表；需要说明使用同一接口的哪些筛选参数，或明确首版不提供详情入口。
- 设置页要求过滤规则、隐私开关、保留设置和接入诊断，但 PATCH 字段 Schema、诊断状态接口和字段说明尚不完整。
- 站点创建、登录、采集和报表已有示例；建议补充 DELETE 任务状态响应、保留期变更预览、暂停恢复，以及异常覆盖元信息示例。
- 将“最多 5 站点”区分为可配置管理上限、产品限制和压测规模。容量按合计 PV、心跳、UV/路径基数和峰值分布评估。
- 90 日浏览器标识与可缩短到 30 日的成员/访客保留关系需明确。若首次访问记录随 30 日清理被删除，仍使用同一 90 日 cid 的回访者可能重新被归为新访客。应独立定义最小身份元数据保留规则，或明确新老分类仅在可观测窗口内成立。
- 365 日日汇总没有新访客字段。早于去重保留期的新访客趋势应明确不可用，或另行定义并保存“按单日口径的新访客数”；它不能替代精确跨日新老分类。
- 小时、分钟、成员和日汇总的实际覆盖窗口应跟随站点配置及成功清理水位，不能在接口错误提示中始终写死 30/90/365 日。

这些是契约补全建议，不要求在本次评审中扩展产品范围。

## R13：资源与运维优化

**部署档位：**原文推荐 2GB，但完整 Compose 示例仍是 1GB 配置。多站点项目建议以 2GB 档为主要部署示例，保留明确标注的 1GB 低负载档；两档均需实测。固定镜像补丁及 digest，按实际负载决定 PostgreSQL 和 Node 内存，不把容器上限当作常驻用量。

**心跳写放大：**`visitors.last_activity_at` 和 `sessions.last_activity_at` 被索引引用，频繁心跳更新会维护索引。对这些更新，仅降低 fillfactor 不能保证使用 HOT。先观测更新量、dead tuples、HOT 比例、autovacuum 和 WAL，再按热表调优。[HOT 条件](https://www.postgresql.org/docs/17/storage-hot.html)

**清理：**分批删除应同时有行数和事务耗时上限，不把 1,000–5,000 行视为固定安全值。普通 VACUUM 主要回收空间供数据库重用，不能保证文件马上缩小；`VACUUM FULL` 会持有排他锁，不适合作为在线日常清理步骤。[VACUUM 说明](https://www.postgresql.org/docs/17/routine-vacuuming.html)

**磁盘与备份：**`max_wal_size=512MB` 是软限制，不能当作 WAL 空间硬上限。磁盘预算需包含临时排序、备份、索引建设和恢复所需空间。[WAL 配置说明](https://www.postgresql.org/docs/17/runtime-config-wal.html)

现有每日加密异机备份可继续对应 RPO≤24 小时的目标，但必须衡量备份快照时间、上传完成时间与任务失败后的缺口。若将来要求小时或分钟级恢复点，另设物理基础备份与 WAL 归档方案；`pg_dump` 不是 PITR 所需的物理基础备份。[PITR 说明](https://www.postgresql.org/docs/17/continuous-archiving.html)

**SDK 首条上报：**可评估首条 PV 立即发送、后续事件再批处理，以尽早取得页面确认并减少短访问丢失互动。改变发送时机后，应重新测峰值请求和批次幂等，不能只看平均请求量。

## R14：补强验收并维护文档同源

保留现有测试分层，新增本报告 R01–R12 的边界场景。性能验收补充：

1. 预置 30 日事实、90 日去重成员和 365 日日汇总，覆盖各自保留规模；30 万 PV 明细不能单独证明 90 日 DISTINCT 的性能。
2. 原文容量假设是每 PV 8 次心跳，而负载配比是心跳 60%、PV 30%，仅为 2:1。保留原基线，并增加符合容量假设的心跳占比、长阅读、多标签和短访问组合。
3. 一个热门站点突发、多个低流量站点正常运行；区分总限流拒绝率和小站延迟。
4. 在采集中同时运行清理、聚合、备份和 autovacuum；测锁等待、临时磁盘和队列积压，不能只测空闲后台。
5. 聚合/删除任务中途终止、正常重启与非正常进程退出、备份恢复后的删除清单重放。
